# SafeDrive 使用者指南：网盘的痛点与解法

这篇文档面向**准备用或正在用 SafeDrive 的人**，不讲实现细节，只回答三个问题：

1. 网盘用着到底哪里难受？
2. SafeDrive 用什么办法解决，哪些能解决、哪些解决不了？
3. 它和 alist / OpenList 这类工具比，取舍在哪？

> 本项目仅供技术学习、研究与管理**本人合法持有的数据**。文末有[合规提示](#合规提示)，请务必读完。

---

## 一、网盘的三类痛点

### 1. 非会员限速

几乎所有国内网盘的共同点：**不开会员，下载速度被人为压到很低**。

关键在于，这个限速通常**不是按账号总带宽限死，而是按「单个连接」限速**。一条连接跑几百 KB/s，开八条就未必只有几百 KB/s。这是能被优化的部分。

### 2. 内容审查（"和谐"）

网盘会对存储的文件做识别（文件名、哈希、内容特征），命中后可能被删除、封禁分享、甚至限制账号。

这里最让人难受的不是"违规内容被删"，而是**误判**：

- 你自己拍的视频、自己写的文档，因为哈希撞上了某个黑名单条目而消失
- 备份的开发资料、镜像文件，因为文件名或特征被判定成"疑似违规"
- 昨天还能下的文件，今天点开提示"文件涉嫌违规，已被冻结"

**百度网盘**在这方面反馈最集中：非会员限速明显，文件也相对容易被和谐。

### 3. 分享限制

**阿里云盘**是典型：

- 普通用户的分享次数有额度限制（社区普遍反馈为每天数次的量级，官方策略随时可能调整）
- 部分文件类型不允许创建分享
- 热门资源的分享链接管控严格，容易失效

于是"存进去容易，分出来难"，网盘退化成一个只进不出的黑洞。

## 二、SafeDrive 怎么解决

### 1. 对付限速：多线程分片下载

SafeDrive 不是把文件整个拖下来再给你，而是**把一个文件切成很多分片，同时用多条连接去拉**，在服务端拼装后以一条普通 HTTP 流交给你的浏览器或播放器。

- **总并发**、**单文件并发**、**单片大小**都可以在「系统设置 → 传输设置」里调（默认 16 线程 / 单卷 4 线程 / 5M 分片）
- **并发是自适应的**：跑得顺就往上加，上游开始报错或变慢就自动退回来，并把学到的合适并发记下来，下次直接用
- **慢链路会被绕开**：百度网盘会拿到多个下载地址，SafeDrive 记录每条的实测表现，主链路卡住时自动改用备选链路
- **在线播放专门优化**：拖动进度条时只取你真正需要的那一段，不会从头下到尾

效果上，单连接被限速的场景下，多线程能把实际速度拉起来。但请注意：

> **它优化的是"单连接限速"，不是绕过会员体系。** 如果网盘对你的账号做的是总带宽限制，多线程能改善的幅度就有限。SafeDrive 不解密、不破解、不伪造会员身份，只是把公开接口能并行的部分并行起来。

另外还有**本地缓存**：从云端拉过的数据块会按 1 MiB 存在本地磁盘，重复观看或反复读取同一文件时直接命中本地，不再回源。缓存存的是**云端原样的密文**，可以按数据源单独开关，也有一个全局总开关。

### 2. 对付内容审查：加密 + 伪装

这是 SafeDrive 的核心。三个**互相独立、可任意组合**的开关：

| 开关 | 做了什么 | 云端看到的 |
| --- | --- | --- |
| **内容加密** | 文件内容用 ChaCha20 加密，密文长度和明文完全相同 | 一堆无法识别的随机字节 |
| **分卷存储** | 一个文件切成多个对象分别落盘 | 若干个小文件，而不是一个大文件 |
| **存储侧伪装** | 每个落地对象前面套一层标准 BMP 头部 | 一张"格式合法"的位图 |

三者任一开启，文件在云端就不再是原来的样子：它落进一个**信封目录**——目录名本身是加密的，里面装着真实文件名、真实大小和这个文件自己的密钥，由上一层目录的密钥解开，一层套一层。整条链的起点是你设置的**根密码**。

对应到痛点上：

- **哈希识别失效**：加密后的字节流和原文件完全不同，哈希自然对不上，不会因为"撞上黑名单"被误删
- **文件名不泄露**：加密数据源里，云端连文件名都看不到（信封目录名是密文，叶子对象名是密钥派生的十六进制凭据）
- **类型识别失效**：开了 BMP 伪装，云端看到的是一张尺寸自洽的位图——名字像、头部也像
- **大文件限制绕开**：分卷让单个落地对象保持在你设定的大小以内

叶子对象叫什么名字也可以自己定（**叶子文件名模版**），可用占位符：

| 占位符 | 含义 |
| --- | --- |
| `{s}` | 原始文件名（含扩展名） |
| `{n}` | 主名（不含扩展名） |
| `{x}` | 扩展名 |
| `{e}` | 文件密钥派生的索引凭据（加密时必填，不泄露任何明文信息） |
| `{i}` | 等宽分卷序号 |

比如 `{n}.{i}.{x}` 会把 `电影.mkv` 落成 `电影.01.mkv`、`电影.02.mkv`；开了加密则强制用 `{e}`，云端只看得到 `3f`、`a1` 这样的名字。配置界面会按当前模版**实时给出示例文件名**，改一个字就能看到落地长什么样。

> **重要：加密解决的是"云端读不懂你的数据"，不是"云端不知道你上传了东西"。** 上传量、文件数量、访问时间这些元信息依然可见。

### 3. 对付分享限制

SafeDrive 的分享**建立在网盘自己的分享接口之上**，所以要分清哪些能解决、哪些不能：

**能解决的：**

- **文件类型限制**：开了伪装后云端存的是 `.bmp`，本来不让分享的类型不再是问题
- **内容管控**：加密后云端识别不出内容，热门资源不会因为特征匹配被掐掉分享
- **分享后仍然可用**：接收方用 SafeDrive 导入 `sd://` 链接，转存到自己的数据源后能**直接解密浏览、在线播放**，不需要先下载再解密

**不能解决的：**

- **分享次数额度**：`sd://` 底层仍是一条真实的网盘原生分享，官方的每日额度照算，SafeDrive 不会也无法绕过

两种分享格式：

- **SafeDrive 标准分享（`sd://`）**：把分享 ID、提取码和解开信封所需的目录密钥打包成一段加密短串。接收方必须用 SafeDrive 导入；两端配置一致时，转存只是云端的一次改名，**内容零重新编码**，秒级完成
- **云盘官网原生分享**：给一条可直接打开的短链（提取码已内嵌），任何人用官方 App 就能打开。仅限**没有加密也没有伪装**的内容——受管条目在云端本来就不是原文件，原生分享给出去对方也用不了

受管条目和外来条目**可以一起选中分享**，会自动打包成一条 `sd://`；导入后受管的仍是受管，外来的仍是外来。

## 三、和 alist / OpenList 比

> 下表是按常见使用场景做的对比，对方的具体行为以其当前版本与文档为准。两类工具的定位本来就不同：alist / OpenList 是**多存储聚合与直链分发**，SafeDrive 是**单人加密数据管理**。

| 维度 | SafeDrive | alist / OpenList |
| --- | --- | --- |
| **加密后在线播放** | 加密 + 分卷 + 伪装三者全开也能直接拖进度条播放，服务端现场解密并支持 Range | 加密驱动下通常必须走代理模式，分卷 / 伪装无对应能力 |
| **分卷存储** | 内置，可设大小与固定/随机策略 | 无 |
| **存储侧伪装** | 内置（BMP），可与加密自由组合 | 无 |
| **网盘原生分享** | 支持创建分享、也支持转存他人分享 | 一般不提供 |
| **加密内容的分享** | `sd://` 打包解密信息，接收方转存后可直接解密使用 | 无对应机制 |
| **配置方式** | 加密、分卷、伪装、命名模版、缓存全在**一个数据源表单**里，每项都有 ⓘ 说明，实时预览落地文件名 | 存储与加密通常是分开的两层（挂载 + crypt 驱动），需要理解两者的组合关系 |
| **数据缓存** | 内置持久密文块缓存，按 1 MiB 落盘，可全局/按数据源开关 | 一般依赖外部方案 |
| **秒传** | 跨数据源复制时自动尝试（阿里云盘、夸克网盘） | 一般不提供 |
| **302 直链** | **不支持**，只有代理下载 | 支持，且是其核心能力 |
| **多用户与权限** | **不支持**，单管理密码 | 支持，可分用户分权限 |
| **存储类型数量** | 5 种（本地 / WebDAV / 百度 / 阿里 / 夸克） | 数十种 |

一句话总结取舍：

- **要把很多种网盘聚合起来、分发直链、多人共用** → alist / OpenList 更合适
- **要把自己的数据加密后放进网盘，还要能随时在线播放、分享、跨盘搬运** → SafeDrive 更合适

两者也**可以叠着用**：SafeDrive 支持接入 WebDAV 数据源，你完全可以把 alist 挂出来的 WebDAV 当作 SafeDrive 的一个存储后端。

## 四、SafeDrive 本身的取舍

### 只做代理，不做 302

所有下载和播放都是**服务端流式代理**：SafeDrive 从云端取回数据、在内存里解密和合卷，再以一条普通 HTTP 流发给客户端。

这不是没做，而是**做不了**：加密数据在云端是分散的密文分卷，302 把客户端直接甩给云端，客户端拿到的是一堆解不开的碎片。要支持加密 + 分卷 + 伪装的在线播放，就必须由服务端居中处理。

代价是**流量和 CPU 都过服务端**——所以它更适合放在家里的机器、NAS 或局域网服务器上，而不是一台小水管 VPS。

### 单用户，面向局域网

SafeDrive **没有多用户和权限管理**，只有一个管理密码（不设置则免登录）。

这是刻意的定位：它是给**个人**用的工具，默认场景是家里或局域网。数据源配置文件里存着网盘凭据和根密码，一个能登录的人就等于拿到全部数据。

> **不建议直接暴露在公网。** 确实需要远程访问时，请放在 HTTPS 反向代理之后，设好管理密码，并做好访问控制。

### 双向 WebDAV

- **作为客户端**：可以把任意 WebDAV 服务加成数据源
- **作为服务端**：把所有数据源以 `/dav/<数据源名>/<路径>` 暴露成一棵标准 WebDAV 树，Finder、Windows 网络位置、rclone、Infuse、nPlayer 都能直接挂载，解密由服务端现场完成，客户端全程只见明文

因为两边都支持，所以**可以自己接自己**——把一个 SafeDrive 实例的 WebDAV 加成另一个实例的数据源，套两层加密。实用价值不大，但确实能跑，图个乐。

WebDAV 服务**默认关闭**，需要在设置里手动开启。

### 在线播放与预览

浏览器里直接看，或者复制外部播放链接丢给 VLC / IINA / Infuse：

- **视频**：mp4 / mkv / webm / mov / m4v / avi / ts
- **音频、图片、PDF**
- **文档**：docx / xlsx / markdown / 纯文本与常见代码文件（纯前端渲染，不出网）

加密、分卷、伪装全开也照常拖进度条——服务端会把你要的那一段换算到对应的分卷、跳过伪装头部、解密后返回。

### 秒传

跨数据源复制时，如果目标网盘已经存在同样的内容，就不必真的上传一遍。

SafeDrive 的做法有个额外好处：**文件密钥跟着复制一起搬**，所以源和目标的每个分卷是**逐字节相同**的对象——加密内容也能吃到秒传，而不是只有明文文件才行。

支持情况：

| 数据源 | 秒传 |
| --- | --- |
| 阿里云盘 | 支持（先用头 1 KiB 廉价预检，命中才算全量摘要） |
| 夸克网盘 | 支持（需 MD5 + SHA1；源端读取昂贵时会跳过） |
| 百度网盘 | **不支持** |
| 本地磁盘 / WebDAV | 不适用 |

两个前提：**两端的加密与伪装设置必须一致**，且**分卷切分跟随源**。任一不满足就退回完整传输——不会静默失败，传输队列里会如实标注"秒传 N 卷 / 实传 N 卷"。

## 五、怎么配比较合适

三个开关是正交的，按你最在意的东西选：

**最在意隐私和防误删** → 加密 + 分卷 + 伪装全开

云端只看到一堆 `.bmp` 小图片，名字和内容都读不懂。代价是不能用官网原生分享，且必须记牢根密码。

**最在意速度和兼容** → 三者全关

就是普通的网盘管理器，仍然享受多线程下载、在线播放、跨盘复制和秒传，但没有任何保护。

**只想绕开单文件大小限制** → 只开分卷

**只想让文件"看起来正常"，不介意内容明文** → 只开伪装

> 三个开关和叶子名模版**创建后不可更改**——读取靠按模版生成候选名再查表，改了就再也认不出已经写下去的数据。想换配置请新建数据源，再用跨数据源复制搬过去。根密码、分卷大小、固定/随机策略、缓存开关则随时可改。

## 六、常见问题

**Q：根密码丢了怎么办？**
数据永久无法读取。没有找回机制——信封目录名、内容密钥全由它派生。请务必备份 `--data-dir` 下的 `datasources.json`（它同时存着网盘凭据和根密码，本身也要妥善保管）。

**Q：能突破会员限速吗？**
能改善单连接限速的场景，不能绕过账号级的带宽限制，也不涉及任何破解或身份伪造。

**Q：加密后网盘还能识别出我传了什么吗？**
识别不出内容，但看得到你传了多少、传了几个文件、什么时候访问。

**Q：分享次数还是被限制怎么办？**
`sd://` 底层是真实的网盘原生分享，官方额度照算，这部分 SafeDrive 帮不上忙。

**Q：手动往加密目录里塞文件会怎样？**
一概静默忽略，不影响读取。SafeDrive 只认按模版生成的候选名。

**Q：转存别人的普通分享到加密数据源里会怎样？**
会作为**外来条目**呈现——不解密也不脱伪装，但照常可以预览、下载、复制播放链接、再分享出去。如果它其实是 SafeDrive 格式的目录，可以用"输入密码解密"把它纳入管理。

**Q：能放公网吗？**
技术上可以，但不建议。没有多用户和权限，一个管理密码就是全部防线。真要放，请套 HTTPS 反代并设好访问控制。
